# view-your-harness

把一个本地目录清点成一个能浏览、能搜、能点开的工作台。一屏看清**我有哪些文件**和**我有哪些 Skill 可用**。

零依赖，只需要 Python 3.8+。只绑 `127.0.0.1`，只读，不联网，不上传任何东西。

---

## 它解决什么问题

另外两个工具回答的是「我这儿哪里有问题」。这个回答的是「我这儿都有什么」。

后者是前者的前置。装到一百多个 Skill 之后，你会遇到这些事：

- 写完一个新 Skill，才想起来早就有一个干同样事的
- 真要干活时想不起自己到底有什么能力
- 两千篇笔记散在几十个目录里，找一篇要翻半天
- 想清理，但不知道哪些是真没用过的

这些问题不需要一份报告，需要一个能翻的架子。

## 快速开始

```bash
git clone https://github.com/SpaceZephyr/build-your-harness.git
cd build-your-harness

python3 view-your-harness/scripts/serve.py <任意目录>
```

它会先跑一遍索引（几秒到半分钟，看目录大小），然后起服务、自动开浏览器。终端打印端口和实际盘的路径。`Ctrl-C` 停止。

```
索引完成 0.6s → /tmp/harness-view/.claude-index.json
  文件 2681  目录 903  体量 78.1 MB
  Skill 191 个（去重后），来自 20 处，19 个重名副本已折叠，另有 6 个裸文件
  调用统计：读 91 个会话日志，11 次调用，9 个 Skill 被真正用过，182 个从未调用

  工作台 → http://127.0.0.1:7799
  盘的是 /Users/xxx/.claude
  只读模式：能看能搜能打开，不改你任何文件。Ctrl-C 停止。
```

### 参数

| 参数 | 用途 |
|------|------|
| `--port 7799` | 指定端口。被占用会自动往后顺延，一般不用管 |
| `--no-open` | 不自动开浏览器（远程 / 无头环境） |
| `--no-usage` | 跳过会话日志统计。日志多时快很多，代价是没有调用次数 |

### 只要数据不要界面

需要拿清点结果做别的分析时，单独跑索引器：

```bash
python3 view-your-harness/scripts/index.py <目录> -o index.json
```

产出是纯事实的 JSON，不含任何判断。

## 工作台里有什么

**顶栏**：目录路径、文件数、目录数、总体量、Skill 数、用过 / 没用过。一个搜索框同时搜文件名、文档标题、Skill 名称和描述。按 `/` 聚焦，`Esc` 关抽屉。

### 文件页

左侧按文件数排的一级目录，点击下钻。

卡片上显示的是**文档标题**（Markdown frontmatter 的 `title` 或第一个 `#`），不是文件名。这个差别比想象中大：满屏的 `report.html` 和 `data.json`，光看文件名分不出谁是谁。

按类型筛（文档 / 代码 / 数据 / 图片 / 音视频 / 配置），按最近改动 / 体量 / 名称排。

### Skill 页

每个 Skill 一张卡：名字、`description`、**真实调用次数**、文件数、体量、最后更新。

筛选：全部 / 用过 / 从未调用 / 元信息不全 / 项目级。

左侧列出所有来源目录，以及 `skills/` 根下的裸 `.md` 文件 —— 那些不是 Skill，永远不会被加载，属于该清理的东西。

### 抽屉

点任意卡片右侧滑出。文本文件看内容，图片直接显示，Skill 看 `SKILL.md` 全文。

三个动作：打开（交给系统默认程序）、在访达中显示、复制绝对路径。

## 三条设计约束

### 只读

服务端没有写、改、删接口。这是设计约束，不是待办。

「可操作」的边界就是**打开**和**定位**：调系统的 `open` 把文件交给你自己的编辑器和访达。要改东西你在编辑器里改，或者用 `better-your-harness` 的修复口令。

### 路径校验只有一处

`serve.py` 的 `_resolve()` 是这个服务唯一的安全边界。相对路径按 root 解析，Skill 卡片的绝对路径额外放行 `~/.claude` 和 `~/.codex`，其余一律 403。

`/api/raw` 只吐图片，不做任意文件下载器。

### 数字只能来自索引器

文件数、Skill 数、调用次数，全部以 `index.json` 为准。脚本没统计的量就显示「未统计」，不显示 0。

## 调用次数的口径

**只认会话日志里 `tool_use(name="Skill")` 的 `input.skill`，不认 Skill 出现在系统提示词的可用清单里。**

这两个口径能差两个数量级。每轮对话都会带上全部可用 Skill 的列表，按关键词 grep 会把每一个 Skill 都算成「用过」。看到别的工具报出「Skill 使用率 100%」，基本就是踩了这个坑。

统计范围是 `~/.claude/projects` 和 `~/.codex/sessions` 下的全部 `jsonl`（上限 1200 个文件）。换过客户端或清过日志就统计不到，这时页面显示「调用次数未统计」而不是 0。

## 同名 Skill 会被折叠

全局装一份、插件市场又带一份的情况很常见。按 `项目 > 全局 > 插件` 留优先级最高的那条，其余折进 `dupes`。

不折叠的话「用过几个」会被重复计数，出现「12 个用过但只有 10 次调用」这种自相矛盾的数字。

## 跟另外两个的关系

```
                    ┌─────────────────────┐
   什么都没有   ──▶  │  star-your-harness  │ ──▶  一个立得住的骨架
                    └─────────────────────┘
                              │
                              ▼
                    ┌─────────────────────┐
   用了一阵    ──▶   │ better-your-harness │ ──▶  覆盖度 + 待办 + 修复口令
                    └─────────────────────┘
                              │
                              ▼
                    ┌─────────────────────┐
   东西堆多了  ──▶   │  view-your-harness  │ ──▶  能翻能搜的工作台
                    └─────────────────────┘
```

体检告诉你该修什么，工作台告诉你手上有什么。修完之后回工作台翻一遍，是确认修完了的最快方式。

## 局限

- 只描述目录当前状态，不评价文件质量，也不判断哪个 Skill 该留该删
- 默认最多索引 20000 个文件，超了会在顶栏标 `+`，不是全量
- 会跳过 `node_modules`、`.git`、`dist`、`.obsidian` 等构建与缓存目录
- 卡片墙一次最多渲染 300 张，剩下的靠搜索缩小范围，不是无限滚动
- **「从未调用」不等于「没用」** —— 刚装的、只看过 reference 的、被别的 Skill 内部引用的，都会显示成从未调用。这是一条线索，不是一条判决
- 只在 macOS / Linux 上测过
